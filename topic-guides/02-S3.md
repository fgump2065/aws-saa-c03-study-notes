# Section 2: S3 — Simple Storage Service

## The idea

S3 is where AWS keeps *stuff*. Not a hard drive, not a filesystem — an **object store**. Think of it as an **infinite valet parking garage for files**: you hand over your file (the "object"), you get a claim ticket (the "key" — its full name, like `photos/2026/cat.jpg`), and whenever you come back with the ticket, you get the whole file back. You can't pop the hood and change the engine while it's parked — **you can't edit a byte in the middle of an object; you replace the whole object**. That's the core difference from a disk (that's EBS) or a shared network filesystem (that's EFS).

Objects live in **buckets**. **General purpose bucket names are globally unique within an AWS partition** (the common namespace is shared across accounts). AWS now also offers an **account-regional namespace**, where only your account can create names. A bucket itself lives in one region you choose. Capacity is unlimited; a single object maxes out at **5 TB**. For big uploads, **multipart upload** splits the file into parallel chunks — **recommended over 100 MB, REQUIRED over 5 GB** (a single PUT caps at 5 GB). S3 designs for **eleven 9s of durability** (99.999999999%) across storage classes, but availability, resilience design (including single-AZ One Zone-IA), retrieval behavior, and cost vary by class. Durability is not a substitute for backups, versioning, or replication.

That "how fast can I get it back and how much does it cost" question is the heart of the exam's S3 questions, so let's build the machine that answers all of them.

## Storage classes and THE 3-filter algorithm

The classes, top shelf to deep freeze (retrieval times and availability are design targets; check the current AWS table for a firm workload/SLA choice):

| Class | Retrieval | Min storage duration | Use when |
|---|---|---|---|
| **Standard** | milliseconds | none | Frequently accessed, hot data |
| **Intelligent-Tiering** | milliseconds | none | **Unknown/unpredictable** access patterns |
| **Standard-IA** | milliseconds | **30 days** | Infrequent access, needs instant retrieval; retrieval fees and a 128 KB minimum billable object size apply |
| **One Zone-IA** | milliseconds | 30 days | Infrequent AND **re-creatable** (one AZ only; retrieval fees and 128 KB minimum billable object size apply) |
| **Glacier Instant Retrieval** | **milliseconds** | **90 days** | Archive touched ~quarterly, needed instantly |
| **Glacier Flexible Retrieval** | Expedited typically **1–5 min** for objects under 250 MB (capacity not guaranteed without provisioned capacity) / Standard **3–5 hr** / Bulk **5–12 hr** | 90 days | Archive, minutes-to-hours retrieval OK |
| **Glacier Deep Archive** | Standard typically **within 12 hr** / Bulk typically **within 48 hr** | **180 days** | Lowest-cost archive tier; plan for hours, not rapid access |

("IA" = Infrequent Access; "AZ" = Availability Zone, one physical data-center cluster.)

Every "most cost-effective storage class" question yields to the same three filters:

**Filter 1 — access frequency picks the family.** Daily/constant → Standard family. Monthly-ish → IA. A few times a year → Glacier family. Unknown → Intelligent-Tiering.

**Filter 2 — the retrieval-time requirement eliminates classes.** *"Needed immediately / within milliseconds"* kills Flexible and Deep Archive (Glacier **Instant** survives — it retrieves in milliseconds). *"Within minutes/hours"* — Flexible is fine (Expedited 1–5 min, Standard 3–5 hr, Bulk 5–12 hr). *"Within 12 hours or more"* — now Deep Archive is on the table. Plan on hours for Deep Archive: AWS describes Standard retrieval as typically within 12 hours and Bulk as typically within 48 hours. These are typical retrieval times, not a universal hard lower bound or guaranteed SLA; choose a faster class when the deadline is strict.

**Filter 3 — minimum storage duration.** IA classes bill a minimum **30 days**, Glacier Instant and Flexible **90 days**, Deep Archive **180 days** — delete early and you pay for the minimum anyway. **Data that lives (or is only kept) under 30 days → Standard is often the sensible choice**, because IA/Glacier minimum-duration and retrieval charges can erase storage savings. Compare workload-specific costs.

**Cheapest class that survives all three filters wins.** Worked example: *"accessed twice a year, auditors need it within 10 minutes, most cost-effective"* → twice a year = Glacier family; "10 minutes" rules out Deep Archive and Flexible Expedited is typically 1–5 minutes for small objects, but is not guaranteed without provisioned capacity. If the deadline is a firm SLA, Glacier Instant Retrieval is safer; if occasional delay is acceptable, Flexible Retrieval can be cheaper.

## The two "special" classes and their exact signals

**One Zone-IA** stores data in a **single Availability Zone** — the AZ burns down, the data is gone. So it's ~20% cheaper and correct **ONLY when the data is re-creatable or a secondary copy**: thumbnails you can regenerate, a replica of on-prem data, secondary backups. The exam signal is the phrase **"can be regenerated / re-created / is a secondary copy."** No such phrase → do not pick One Zone.

**Intelligent-Tiering** watches each object and moves it between tiers automatically. Sounds like a free lunch; it isn't:

- There's a **monitoring fee per object** — millions of tiny objects = real money.
- **Objects under 128 KB are never tiered** (they just sit at Standard rates).
- An object pays **Standard price for ~30 days** of observed inactivity before IT moves it down.

So: **if you KNOW the pattern ("accessed heavily for 30 days, then rarely"), a lifecycle rule beats Intelligent-Tiering** — it's cheaper and deterministic. IT is a strong fit when access is unknown, unpredictable, or changing; it is not the only possible use.

## Lifecycle, versioning, replication

**Lifecycle rules** = the automated conveyor belt: *transition* actions move objects down the class ladder on a schedule ("after 30 days → Standard-IA, after 90 → Glacier, after 365 → delete"), *expiration* actions delete them. Also great for cleaning up old versions and **aborting incomplete multipart uploads** (which silently cost money forever otherwise).

**Versioning** keeps every version of every object. Overwrite = new version on top; delete = a **delete marker** placed on top (the old versions are still there — remove the marker and the object "reappears"). It's the answer to *"protect against accidental overwrite/deletion."* Once enabled, versioning can be suspended but not returned to the never-versioned state; existing versions remain. Add **MFA Delete** can require MFA for permanently deleting a version and changing versioning state. It must be configured by the root user using MFA; the management workflow has specific API/CLI limitations.

**Replication** copies objects to another bucket automatically:

- **CRR** (Cross-Region Replication) → different region: compliance, disaster recovery, lower latency for far-away users.
- **SRR** (Same-Region Replication) → same region: log aggregation into one bucket, prod → test copies.
- Requires **versioning ON in both buckets**.
- **THE trap:** replication copies **NEW objects only**, from the moment you enable it. *"Existing objects must be replicated too"* → **S3 Batch Replication**.

## The encryption ladder (sorted by how little you trust AWS)

Quick jargon: encryption **at rest** = scrambled while sitting on disk. Encryption **in transit** = scrambled while traveling over the network, done by **TLS** (Transport Layer Security — the "s" in https, the standard protocol that encrypts web traffic). **KMS** = AWS Key Management Service, the managed vault for encryption keys.

Climb the ladder as trust in AWS decreases and your effort increases:

| Rung | Who holds the key | Why pick it |
|---|---|---|
| **SSE-S3** (AES-256) | AWS, fully managed | **Default** on all new objects. Zero effort. "Just encrypt it" |
| **SSE-KMS** | A KMS key you control in your account | **Audit every key use in CloudTrail**, control rotation, decide who may decrypt. **"Audit" is its keyword** |
| **SSE-C** | **You** supply the key **on every request** | AWS's CPUs do the encrypting but never store your key; key travels per request **over HTTPS** (mandatory) |
| **Client-side** | You, entirely | You **encrypt BEFORE upload; AWS never sees plaintext**, ever |

(SSE = Server-Side Encryption — S3's servers do the crypto work for the first three rungs.)

SSE-KMS fine print worth points: heavy traffic can hit **KMS API request limits** (every object touch calls KMS). **S3 Bucket Key** fixes this — one bucket-level key cuts **KMS API costs ~99%** — BUT fewer KMS calls means a **coarser per-object audit trail** in CloudTrail. Cost fix with an audit trade-off.

Three encryption traps:

- **"Encrypt in transit" = TLS/HTTPS**, not KMS. Don't let a KMS answer seduce you on a transit question.
- **Enforce HTTPS** → bucket policy that **Denies** requests where **`aws:SecureTransport` = `false`**. Classic exam answer, verbatim.
- Turning encryption on **does not touch existing objects** — encryption applies at write time. *"Encrypt all EXISTING objects"* → **S3 Batch Operations** (re-writes them encrypted).

## Object Lock: WORM

**Object Lock** provides **WORM** (Write Once, Read Many) protection for object versions. During retention, a protected version cannot be deleted in Compliance mode; Governance can be bypassed by an authorized principal. A new version can still be written at the same key, so Object Lock does not make the key itself immutable. **Versioning is required**. Object Lock can be enabled when creating a bucket **or on an existing general purpose bucket**; after enabling it, you cannot disable Object Lock or suspend versioning.

| Mode | Who can delete during retention | Exam signal |
|---|---|---|
| **Compliance mode** | No user, including root, can delete the protected version during retention. | "regulators require," "even administrators must not delete" |
| **Governance mode** | Authorized users with `s3:BypassGovernanceRetention` can bypass protection when explicitly requesting it | "protected, but privileged users may override" |
| **Legal Hold** | No one, **indefinitely — no expiry date, stays until explicitly removed** | "**lawsuit**," litigation, "until the case closes" |

**THE trap:** "even administrators / even the root user cannot delete" → **Compliance**, never Governance.

## Who can get in: access controls

- **Block Public Access** — public-access guardrails, **on by default for new buckets** (and separately configurable at account level). They block public access through applicable policies and ACLs. *"Bucket policy allows public read but access still fails"* → check Block Public Access. *"Guarantee nothing is ever public org-wide"* → enforce it across accounts. **Object Ownership defaults to Bucket owner enforced** on new buckets, disabling ACLs; AWS recommends policies over ACLs for most use cases.
- **Bucket policies** — resource-based JSON policies (Section 1!) on the bucket: cross-account grants, enforce HTTPS, require encryption headers, IP restrictions.
- **Presigned URLs** — a time-limited signed link to one object: *"let a customer download this private file for 20 minutes, no AWS account needed."* The URL is authorized using the credentials of whoever created it (creator can't access the object → URL won't work). With SigV4, the URL can be valid for **up to 7 days**, but temporary credentials can make it expire sooner.
- **OAC (Origin Access Control)** — when CloudFront (AWS's CDN — content delivery network, a global fleet of caching edge servers) sits in front of your bucket, OAC lets **only CloudFront** fetch from the bucket, so nobody can bypass the CDN and hit S3 directly. Signal: *"users must access content only through CloudFront."* (You may see the older name OAI — OAC is the current answer.)

## Access Logs vs CloudTrail

**S3 Server Access Logs** record detailed request activity for a bucket, delivered as log files to *another* bucket. **THE trap: never log a bucket to itself** — each delivered log file is a new request, which writes a new log... an **infinite loop** that bloats your bill. Always a **separate target bucket**. Logs can be delivered to another S3 general purpose bucket or CloudWatch Logs; use Athena/CloudWatch Logs Insights for analysis. S3 server access logging is best-effort and is **not a complete accounting** of requests.

| | S3 Access Logs | CloudTrail data events |
|---|---|---|
| Cost | Basically free (storage only) | Paid per event |
| Delivery | **Best-effort**, usually within a few hours; can be late, duplicated, or missing | Depends on trail/event data store configuration; near real-time delivery is not a hard guarantee |
| Detail | Request-level, but **not a complete accounting**; can omit or duplicate records | Identity and API details; object-level S3 data events must be explicitly enabled and incur charges |
| Pick when | Operational traffic analysis; delivery has no S3 logging fee, but destination storage/queries can cost | Auditing object API activity and identities; configure the required S3 data events and alerting |

## Performance

- Baseline: S3 can support at least **3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per partitioned prefix**. Actual rates vary and scaling is gradual, not instantaneous. If you need higher throughput, parallelize across prefixes and connections; do not add random key prefixes by default unless the workload needs them.
- **Multipart upload** — parallel chunks for big files: recommended >100 MB, required >5 GB, and a failed part retries alone.
- **Transfer Acceleration** — for **UPLOADS from users around the globe into ONE central bucket**: they upload to the nearest CloudFront edge location, then the data rides **AWS's private backbone** to the bucket. You **pay only if it's actually faster** than a normal upload. Signal: *"users worldwide upload large files to a central bucket, speed it up."* For global **downloads**, the answer is **CloudFront**, not TA.
- **Byte-range fetches** — GET just a slice of an object (`Range` header): parallel downloads, or grab only the header/footer of a huge file.

## Events and querying

- **Event notifications** — "when an object lands (or is deleted), do something": target **Lambda, SQS, SNS**, or **EventBridge** (EventBridge unlocks richer filtering and fan-out to many services). Classic: *"generate a thumbnail whenever an image is uploaded"* → S3 event → Lambda.
- **S3 Select** — historically ran SQL against one object (CSV/JSON/Parquet), but is **no longer available to new customers**. Existing customers can continue using it. For new workloads, consider Athena or another query service, often with columnar formats and partitioning.
- **Athena** — SQL **across many objects/whole buckets**, serverless, pay-per-query. Signal: *"analyze/query logs stored in S3 with standard SQL."* For new customers, use Athena or another query service for both single-object and data-set queries; existing S3 Select customers may still use it for a single object.

## Question patterns

> *"Compliance data accessed about twice a year; auditors must receive it within 10 minutes. Most cost-effective class?"* → **Glacier Flexible Retrieval** (Deep Archive is designed for retrieval in hours (typically within 12 hours Standard / 48 hours Bulk); Instant passes but costs more; Flexible Expedited = 1–5 min).

> *"Records retained 7 years, almost never accessed, retrieval within 2 business days is acceptable. Cheapest?"* → **Glacier Deep Archive** (deadline ≥ 12 hr finally lets the cheapest class survive).

> *"Reports are heavily used for 30 days, rarely after 90, must always be retrievable in milliseconds."* → **Lifecycle rule: Standard → Standard-IA at 30 days → Glacier Instant Retrieval at 90** (known pattern → lifecycle; "milliseconds" keeps you in Instant, out of Flexible).

> *"Access patterns are unknown and unpredictable; minimize cost without performance impact."* → **Intelligent-Tiering** ("unknown/unpredictable" is its one and only signal).

> *"Thumbnails can be regenerated from originals at any time; store infrequently accessed copies cheaply."* → **One Zone-IA** ("can be regenerated" = single-AZ risk is acceptable).

> *"Processing artifacts are deleted after 20 days. Cheapest class?"* → **S3 Standard** (under every minimum duration — IA/Glacier would bill 30–180 days anyway).

> *"Security must audit exactly when each encryption key was used, and control key rotation."* → **SSE-KMS** ("audit key usage" is the KMS keyword; add S3 Bucket Key if the question moans about KMS request costs).

> *"Regulatory requirement: data must be impossible to delete for 5 years — even by administrators."* → **Object Lock, Compliance mode** ("even administrators" rules out Governance).

> *"Objects must be preserved indefinitely while litigation is pending."* → **Legal Hold** ("lawsuit" + no fixed end date).

> *"Users on every continent upload multi-GB video files to a single S3 bucket; speed up uploads."* → **Transfer Acceleration + multipart upload** (global UPLOAD to one bucket; global download would be CloudFront).

> *"All objects must be encrypted in transit."* → **Bucket policy denying requests where `aws:SecureTransport` is false** (in transit = HTTPS/TLS, not KMS).

> *"Enable access logging for a bucket — what's the key configuration rule?"* → **Deliver logs to a DIFFERENT bucket** (same bucket = infinite logging loop); query them with **Athena**.

> *"Replication was enabled but existing objects didn't copy over."* → **S3 Batch Replication** (CRR/SRR only replicate NEW objects).

## Pocket card

| Keyword | Answer |
|---|---|
| Frequently accessed / hot | S3 Standard |
| Lives < 30 days | Standard (minimum-duration charges kill the rest) |
| Infrequent + instant retrieval | Standard-IA |
| "Can be regenerated / secondary copy" | One Zone-IA |
| "Unknown / unpredictable access" | Intelligent-Tiering |
| Known pattern over time | Lifecycle rule (beats Intelligent-Tiering) |
| Archive + milliseconds retrieval | Glacier Instant Retrieval |
| Archive + minutes-to-hours OK | Glacier Flexible (Expedited typically 1–5 min for <250 MB (capacity caveat) / Std 3–5 hr / Bulk 5–12 hr) |
| Lowest-cost long-term archive; hours acceptable | Glacier Deep Archive (typically within 12 hr Standard / 48 hr Bulk) |
| Object > 5 GB (or > 100 MB) | Multipart upload (required / recommended) |
| Accidental delete/overwrite protection | Versioning (+ MFA Delete for root-MFA-gated deletes) |
| Copy to another region, DR/compliance | CRR (versioning on both sides) |
| Aggregate logs / copy within region | SRR |
| Replicate EXISTING objects | S3 Batch Replication |
| Default encryption, zero effort | SSE-S3 |
| "Audit key usage" / control rotation | SSE-KMS (in CloudTrail) |
| KMS request costs too high | S3 Bucket Key (~99% fewer KMS calls, coarser audit) |
| Customer supplies key per request | SSE-C (HTTPS mandatory) |
| "AWS must never see plaintext" | Client-side encryption |
| Encrypt in transit / enforce HTTPS | Deny aws:SecureTransport = false |
| Encrypt EXISTING objects | S3 Batch Operations |
| WORM, "not even root can delete" | Object Lock — Compliance mode |
| WORM, privileged users may bypass | Object Lock — Governance mode |
| "Lawsuit," indefinite hold | Legal Hold |
| Temporary download link, no AWS account | Presigned URL (creator's perms, ≤ 7 days) |
| Public policy exists but access fails | Block Public Access is on |
| S3 reachable only via CloudFront | OAC |
| Who accessed — cheap/complete/delayed | S3 Server Access Logs (different bucket! + Athena) |
| Who accessed — real-time + IAM identity | CloudTrail data events |
| More requests/sec | More prefixes (3,500 PUT / 5,500 GET per prefix) |
| Global UPLOADS to one bucket | Transfer Acceleration (pay only if faster) |
| Global DOWNLOADS | CloudFront |
| Download part of an object | Byte-range fetch |
| "When object uploaded, trigger..." | Event notification → Lambda/SQS/SNS/EventBridge |
| SQL on ONE object | S3 Select (existing customers only); otherwise use Athena/another query service |
| SQL across S3 data sets | Athena |

S3's bucket policies are just Section 1's resource-based policies wearing a storage hat — and its classes ladder is the warm-up for the same cost-vs-speed reasoning you'll reuse on EBS, EFS, and Glacier-style questions everywhere else on the exam.
